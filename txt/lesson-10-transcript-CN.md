命中断点后，Stack1 视图里能看到数组 `foo`，说明这个数组确实在栈上。

等等，更有意思的在后面——`fact()` 调用自己之后，你会看到栈又多了一个 `foo` 数组的实例。

When `fact()` calls itself yet again, another instance of `foo` is added on top of the stack.

`fact()` 再次调用自己时，又一个 `foo` 实例被压到栈顶。

OK, so the stack grows much faster with the `foo` array than without it, but I hope you noticed that each instance of `foo[]` contains some values. A good question to ask is: what's this stuff and where is it coming from?

好了，加了 `foo` 数组之后，栈的增长速度快了很多。不过我希望你注意到，每个 `foo[]` 实例里面都有一些数据。好问题来了：这些东西是什么？从哪来的？

Well the answer is the stuff comes from previous uses of the RAM. This particular data looks like the flash memory image, most likely left by the flash loader that programmed your code into the Flash ROM.

答案是：这些数据是 RAM 之前使用后留下来的。具体看这些数据，像是 Flash 内存映像，很可能是烧录器把代码写进 Flash ROM 时留下的。

But the most important fact to remember is that the content of the stack is garbage for your intents. In other words, you cannot assume that any **automatic variable** has any particular initial value, but instead you have to explicitly initialize every automatic variable to the value you need.

但最重要的一点你要记住：栈里的内容对你来说就是垃圾。换句话说，你不能假设任何**自动变量**（automatic variable）有什么特定的初始值——你必须自己显式地把每个自动变量初始化成你需要的值。

To help you remember this critically important fact, let me extend the metaphor of the stack of dishes I offered two lessons ago. The call stack is like a stack of dishes, but they are all dirty. It is just disgusting to use them before first washing them clean.

为了帮你记住这个极其重要的事实，我把两节课前的"一摞盘子"比喻再扩展一下。**调用栈**（call stack）就像一摞盘子，但这些盘子全是脏的——不洗干净就直接用，那太恶心了。

好了，这个压力测试确实在猛敲栈，但还没把它敲破。

那我们回到代码，把 `foo` 的大小提高一个数量级到 100，更狠地敲它。

This time around, before you run the code, I'd like to show you yet another view of the stack available in the IAR debugger. Please click the View menu and select Call Stack.

这次在运行代码之前，我想再给你看一个 IAR 调试器里的栈视图。点 View 菜单，选 **Call Stack**（调用栈视图）。

As the name suggests, the Call Stack view shows all the function calls currently nested on the stack. Interestingly, below `main` you can see another function, which means that `main` itself was called from `_call_main`. 顾名思义，Call Stack 视图显示的是当前嵌套在栈上的所有函数调用。比如你现在停在 `main()` 函数的开头，Call Stack 顶部就显示 `main`。有趣的是，`main` 下面还有另一个函数，说明 `main` 本身是被 `_call_main` 调用的。这是所谓的**启动代码**（startup code）的一部分，后面的课程我会专门讲。

But back to our torture session of the stack, make sure that the breakpoint inside `fact()` is still set, and run the code.

回到我们折磨栈的环节——确认 `fact()` 里的断点还在，然后运行代码。

When you hit the breakpoint now, you can see the much bigger `foo` array on the stack, while the Call Stack view confirms that you are inside the `fact()` function called from `main`.

命中断点后，你会看到栈上的 `foo` 数组大了很多，Call Stack 视图也确认你正处于从 `main` 调用的 `fact()` 函数内部。

Now, you can see that `fact()` function starts to call itself recursively and that the stack grows very fast.

接下来你会看到 `fact()` 开始递归调用自己，栈增长得飞快。

When you reach 5 levels of call nesting, you exhaust your stack completely. The stack pointer is exactly at the beginning of RAM and has no more room to grow towards even lower addresses, because there is no memory there.

当递归嵌套到第 5 层的时候，栈空间就彻底耗尽了。栈指针正好在 RAM 的起始位置，再往下已经没有内存了，没法继续增长。

Now it's getting really exciting, and I hope that you are hanging by edge of your seat. So, continue and watch what happens.

这下精彩了，希望你坐稳了。继续运行，看看会发生什么。

Well, for starters, your program freezes and doesn't hit the breakpoint.

结果就是——程序卡死了，断点根本没命中。

So, let's manually break into the code. As you can see, the stack pointer is below the valid RAM, which begins at 0x2 followed by all zeroes,

手动暂停程序看一下。你会看到栈指针已经跑到有效 RAM 范围之外了——有效 RAM 从 0x2 后面跟一串零的那个地址开始，

and the program hangs in an endless loop around `BusFault_Handler`.

程序卡在了 `BusFault_Handler` 的死循环里。

This, of course, calls for some explanation. The `BusFault_Handler` is not your code, but rather is the so called **exception handler** provided in the standard IAR startup code, which is linked with your main program by the **linker**. The **BusFault exception** is a hardware mechanism implemented in the CPU to handle the situation when the CPU is forced to access nonexistent memory. The IAR startup code implements the BusFault exception as well as all other exceptions as an endless loop, but you can actually provide your own code that could do something else, for example reset the CPU. I will show you how to define your own exception handlers in a lesson about the startup code.

这当然需要解释一下。`BusFault_Handler` 不是你写的代码，而是 IAR 标准启动代码里提供的**异常处理程序**（exception handler），由**链接器**（linker）跟你的主程序链接在一起。**BusFault 异常**是 CPU 里的一种硬件机制，当 CPU 被迫访问不存在的内存地址时就会触发。IAR 启动代码把 BusFault 和其他所有异常都实现成了死循环，但你可以写自己的处理代码，比如让 CPU 复位。后面讲启动代码的课程中我会教你怎么自定义异常处理程序。

At this point I'd like to congratulate you for experiencing your first **stack overflow**. Now you will know how it feels and I hope you will develop a habit of checking the stack pointer when you find your program hanging inside a hardware exception. Note, however, that stack overflow can fail in some other ways as well, such as only corrupt some data, but not run out of memory, which can be much harder to detect and diagnose.

恭喜你，经历了人生第一次**栈溢出**（stack overflow）！现在你知道那是什么感觉了。以后发现程序卡在硬件异常里，希望你第一反应就是去检查栈指针。不过要注意，栈溢出不一定都是这种表现——有时候它只是悄悄破坏了一些数据，内存并没有用完，这种反而更难发现和排查。

In any case, you should develop a habit of sizing the stack adequately for your specific application, so that you don't ever run out of stack.

不管怎样，你应该养成一个好习惯：根据具体应用合理设置**栈大小**，确保永远不会把栈用完。

How do you change the stack size? Open the project options and select the linker category. Under the config tab, check the override default, because you are about to change the default stack size setting.

怎么改栈大小呢？打开项目选项，选 Linker 这一栏。在 Config 标签页里勾选"override default"，因为你要改的就是默认栈大小。

Click the Edit button and select the Stack/Heap Sizes tab.

点 Edit 按钮，选 Stack/Heap Sizes 标签页。

The default stack size turns out to be 2KB, specified here in hex, but you can use decimal. I believe that 1KB of stack should be adequate for all your projects at this stage. Of course, assuming that you remove the hack from the factorial function.

默认栈大小是 2KB，这里显示的是十六进制，不过你也可以输入十进制。我认为现阶段你所有的项目，1KB 的栈应该就够用了。当然，前提是你得把阶乘函数里那些用来施压的代码删掉。

The **heap** is the region of RAM for dynamic memory allocation with the standard functions `malloc` and `free`. This is quite useful in general-purpose computing, but in real-time embedded programming the heap typically causes more harm than good and you should not use it, in which case you should set the heap size to 0.

**堆**（heap）是 RAM 中用于动态内存分配的区域，通过标准函数 `malloc` 和 `free` 来使用。通用计算里这个很有用，但在实时嵌入式编程中，堆通常是弊大于利的——你最好别用它，所以把堆大小设成 0 就对了。

After you click the Save button, you need to choose the location of the edited IAR linker script `project.icf`. You need to save this file, because it is no longer default and now contains settings specific to your project.

点 Save 按钮之后，你要选一下编辑后的 IAR 链接脚本 `project.icf` 存到哪。这个文件必须保存，因为它已经不再是默认配置了，里面包含的是你项目特有的设置。

Now, let's create another, more subtle disaster in the code. This time, you will corrupt the stack and watch how this blows up. Not to give away too much, I only want to tell you that you will witness a mystery worthy Sherlock Holmes.

接下来，我们在代码里制造另一场更隐蔽的灾难。这次你要破坏栈，然后观察它是怎么崩的。不剧透太多，我只能说——你将见证一个值得福尔摩斯出手的谜案。

To prepare the crime scene, go to the `fact()` function, and change the size of the `foo` array to 6. Next, go up to `main`, and call `fact` with the argument of 7 and set a breakpoint at this call. I hope you start to see where this is going...

先准备一下"犯罪现场"：到 `fact()` 函数里，把 `foo` 数组大小改成 6。然后回到 `main`，用参数 7 调用 `fact`，并在调用处设个断点。我希望你已经猜到接下来会发生什么了……

Run the code to the breakpoint, and single step from there.

运行代码到断点处，然后开始单步执行。

The `PUSH R4, LR` should be familiar from the last lesson.

`PUSH R4, LR` 这条指令你上节课应该已经熟悉了。

But the subtraction from the stack pointer is new. This is how your `foo` array is allocated on the stack. You see here that SP is reduced by 0x18 bytes, which only makes some room on the stack, but no cycles are wasted to clean the space. That's why the `foo` array contains garbage.

但接下来从栈指针减去一个数的操作是新的——这就是你的 `foo` 数组在栈上分配空间的方式。SP 减了 0x18 字节，只是在栈上腾出了一块空间，并没有花任何周期去清零。所以 `foo` 数组里全是垃圾数据。

The `ADD` instruction puts the address of the `foo` array, which happens to be the current top of the stack, into R1.

`ADD` 指令把 `foo` 数组的地址——也就是当前栈顶——放进了 R1。

The `STR` instruction writes the value `n` from R0 to the index `n`, which is also R0. The logical-shift-left by 2 is accounting for the fact that each element of `foo` takes 4-bytes.

`STR` 指令把 R0 里的值 `n` 写入索引 `n` 的位置（索引也是 R0）。逻辑左移 2 位是因为 `foo` 的每个元素占 4 个字节。

Now watch carefully at the effect of the `STR` instruction, because the crime happens right here. The last valid index of `foo` is 5, so the index 7 goes two locations beyond the end of `foo`. This location happens to be the saved **LR register**, which is now corrupted and the function will not be able to return correctly.

现在仔细看 `STR` 指令的效果——因为"犯罪"就发生在这里。`foo` 最后一个合法索引是 5，索引 7 已经超出了 `foo` 两个位置。这个位置恰好是保存在栈上的 **LR 寄存器**（链接寄存器，Link Register），现在它被破坏了——函数没法正确返回了。

So the crime is actually quite simple. You indexed an array **out of bounds** and corrupted the stack. Note that the C language allows you to do this very easily, because C does not check array indexes and trusts that you know what you are doing.

所以"犯罪"过程其实很简单：你对数组进行了**越界访问**（out of bounds），把栈给破坏了。注意，C 语言让你很容易犯这种错，因为它不检查数组索引，默认你知道自己在干什么。

However, like in any good mystery, that's not the crime that is interesting, but the story that unfolds. As it turns out, the story unfolds here for thousands of clock cycles, before the system finally fails. Obviously, the art of debugging such problems is to avoid single stepping for thousands of steps. Instead, you should learn how to set your breakpoints strategically.

不过，就像任何好的推理故事一样，有趣的不是犯罪本身，而是之后的发展。事实上，这个"故事"会持续数千个时钟周期，系统才会最终崩溃。显然，调试这类问题的技巧在于——别傻乎乎地单步执行几千步。你应该学会策略性地设置断点。

The first strategic location is the return from `foo`. It's logical to stop there, because you know that the problem is with the return address.

第一个策略性位置是从 `foo` 返回的地方。在那里停下来很合理，因为你已经知道问题出在返回地址上。

When you hit this breakpoint, all the recursive calls to factorial are nested on the stack. This is the maximum use of the stack, and you can verify that you don't have the stack overflow problem.

命中这个断点时，所有递归调用都嵌套在栈上。这是栈使用量最大的时候，你可以确认一下没有栈溢出的问题。

When you continue from here, you gradually un-wind the stack as each nested call returns. I think it's beautiful to watch.

从这里继续运行，随着每一层递归调用返回，栈逐渐展开——这个过程看着真的很美。

Finally, you are down to the last call and a very small stack. The `ADD` instruction removes the size of the `foo` array from the stack.

最后只剩下一层调用，栈也很小了。`ADD` 指令把 `foo` 数组占用的空间从栈上释放掉。

And the last `POP R4, PC` instruction performs the final return. Note that the return address that is about to be restored into the PC is 7. This is the corrupted value, which I have carefully planned to be odd, because if it was even, the `POP` instruction would fail right here and the CPU will go into exception, which will end the story. (In case you forgot why every return address must be odd on Cortex-M, please go back to lesson 8).

最后一条 `POP R4, PC` 指令执行最终的返回。注意，即将恢复到 PC 里的返回地址是 7——这是我精心设计的被破坏的值。我特意让它是个奇数，因为如果是偶数，`POP` 指令直接就失败了，CPU 会进入异常，故事也就到此结束了。（忘了为什么 Cortex-M 上返回地址必须是奇数？回到第 8 课复习一下。）

So, by my careful and pervert planning the `POP` instruction succeeds and the Program Counter is forced to 6.

所以，经过我精心又有点变态的设计，`POP` 指令居然成功了，**程序计数器**（Program Counter, PC）被强制设成了 6。

Frankly, what happens now took me by surprise, because the disassembly view is actually misleading. The problem is that these low memory locations are used for the so-called **exception and interrupt vector table**, which means a bunch of 32-bit memory addresses. But somehow, the CPU executes this data as legit 16-bit instructions, whereas it takes two disassembly steps per each 32-bit data value.

说实话，接下来发生的事连我都很意外——因为反汇编视图其实是有误导性的。问题在于这些低地址内存区域存放的是所谓的**异常和中断向量表**（exception and interrupt vector table），里面是一堆 32 位的内存地址。但 CPU 居然把这些数据当成合法的 16 位指令来执行了——而每个 32 位数据值恰好对应两条反汇编指令。

By sheer coincidence, the `main` function immediately follows the vector table in the Flash ROM, so now the CPU starts to execute real instructions. The first one is push to the stack, but the stack already has the previously pushed registers from `main`, because remember that `main` has never really returned.

纯粹是巧合，`main` 函数在 Flash ROM 中紧跟在向量表后面，所以 CPU 接下来开始执行真正的指令了。第一条是压栈指令，但栈上已经堆着之前 `main` 压入的寄存器——别忘了，`main` 从来没有真正返回过。

When you continue from here, you end up hitting the breakpoint still present at the return from factorial. Remove this breakpoint and continue.

从这里继续运行，你最终又会命中之前设在阶乘函数返回处的断点。把这个断点删掉，继续运行。

So now you have only one breakpoint left at the call to factorial of 7.

现在只剩下一个断点了，就是调用 factorial(7) 那个地方。

From now on, each time you hit the continue button, you execute the whole cycle of recursive calls, corrupting the stack, and re-entering `main` through the back door of executing the vector table. Please note however, that the stack keeps slowly growing, because `main` does not really return, so it does not POP its stack frame from the stack.

从现在开始，每点一次继续，就执行一整套递归调用周期——破坏栈、通过执行向量表的后门重新进入 `main`。但请注意，栈在持续缓慢增长，因为 `main` 并没有真正返回，所以它的**栈帧**（stack frame）不会被弹出。

Finally, remove the last breakpoint and let the program run. At this point, you should know how it will end up. Because the stack is growing, you eventually overflow it and the CPU enters the BusFault exception.

最后，把最后一个断点也删掉，让程序自由运行。到这时候你应该知道结局了——栈一直在增长，最终溢出，CPU 进入 BusFault 异常。

With this mystery solved, I hope you gained some respect for corrupting the stack. I mean, this can get really nasty really fast with a runaway program corrupting its state sometimes for thousands of CPU cycles. This tends to be very hard to reproduce and debug, because there can be so many coincidences along the way.

谜案解开了。希望你对栈破坏这件事多几分敬畏。我是说，失控的程序可能在数千个 CPU 周期内不断破坏自身状态，局面恶化得非常快。这类问题往往极难复现和调试，因为过程中有太多巧合了。

In the last segment of this lesson I'd like to shift the gear a bit and talk about function arguments, including pointer arguments, and returning pointer values from functions.

这节课的最后一部分，换个话题，聊聊函数参数——包括指针参数——以及从函数返回指针值。

Let's start with an experiment, in which you modify the `delay` function to decrement its argument `iter` as long as it is greater than zero. This example is intended to show you that function arguments are just like local variables which you can modify. The only difference is that arguments are initialized by the caller and local variables must be initialized inside the function.

先做个实验：修改 `delay` 函数，让它在参数 `iter` 大于 0 的时候不断递减。这个例子想说明的是，函数参数跟局部变量一样，你是可以修改它的。唯一的区别在于：参数由调用者初始化，而局部变量必须在函数内部自己初始化。

As usual for delay loops, make the loop counter `volatile` to prevent the compiler from optimizing the while loop away. Because now you've changed the signature of the function, don't forget to update the function prototype in the header file.

跟以前写延时循环一样，把循环计数器声明为 `volatile`，防止编译器把 while 循环优化掉。既然你改了函数的**签名**（signature），别忘了同步更新头文件里的函数**原型**（prototype）。

Before you run this program, change the way you call `delay()` to pass a variable `x` as the argument instead of the constant.

运行程序之前，改一下调用 `delay()` 的方式——传一个变量 `x` 进去，而不是传常量。

Set a breakpoint at the first call to delay and immediately after the call.

在第一次调用 delay 的地方设个断点，调用结束后紧跟着也设一个。

At the first breakpoint, verify that variable `x` has the value 1 million.

在第一个断点处，确认变量 `x` 的值是 100 万。

At the second breakpoint immediately after the call, you can see that `x` has still the value 1 million, even though delay has decremented its argument to 0.

在调用结束后紧接着的第二个断点处，你会看到 `x` 的值仍然是 100 万——虽然 delay 函数内部已经把参数递减到了 0。

Remove the breakpoints and run the program free to see if the Launchpad board still blinks the LED. And so it does.

清除断点，让程序自由运行，看看 LaunchPad 板上的 LED 还在不在闪。还在闪。

The conclusion of this little experiment is that C passes function arguments **by value**, meaning that only the argument's value is copied to the internal variable to initialize it, but internally the function uses this copy rather than the original argument. This means that a function will never change the original argument.

这个小实验的结论是：C 语言是**按值传递**（pass by value）参数的。也就是说，只有参数的值被复制到函数内部的变量里，函数用的是这个副本，而不是原始的那个变量。所以函数永远不会改变调用方传入的原始参数。

But sometimes you might want exactly to change the arguments. The classic example is the **swap** operation, which exchanges the values of its arguments `x` and `y`.

但有时候你恰恰就需要改变参数。经典的例子就是**交换**（swap）操作——把参数 `x` 和 `y` 的值互换。

Your first attempt might be to write the swap function as follows: store the value of `x` in a temporary, copy `y` to `x`, and copy the temporary to `y`.

你可能会先这样写 swap 函数：把 `x` 的值存到一个临时变量，把 `y` 复制给 `x`，再把临时变量复制给 `y`。

You should also provide a prototype of this function, because the compiler is set up to require prototypes.

别忘了提供函数原型，因为编译器配置的是必须要有原型声明。

The use case of your swap function might be as follows: declare `x` initialized to 1, declare `y` initialized to 2, and swap these two variables.

使用方式可能是这样：声明 `x` 初始化为 1，声明 `y` 初始化为 2，然后交换这两个变量。

Except, of course, this does not work, because the swap function cannot change the arguments. And this is where you need the indirection of pointers used as arguments.

当然了，这样做是不行的——swap 函数改不了参数。这时候就需要用到指针参数的**间接访问**（indirection）了。

The conversion to pointers is easy and the C syntax actually helps you. Simply change `x` and `y` into `*x` and `*y`.

改成指针很简单，C 语法也在帮你。只要把 `x` 和 `y` 改成 `*x` 和 `*y` 就行。

Finally, you need to adjust the function call to take address of `x` and address of `y`, because now the signature requires pointers to integers, not just integers.

最后还得调整函数调用——传入 `x` 的地址和 `y` 的地址，因为现在函数签名要求的是指向整数的指针，不再是整数本身了。

Let's quickly test this code.

来快速测试一下这段代码。

As you can see, the addresses of `x` and `y` are prepared in R0 and R1, according to the **ARM Procedure Call Standard**.

可以看到，`x` 和 `y` 的地址分别放在了 R0 和 R1 中——这是符合 **ARM 过程调用标准**（AAPCS）的。

The value of `x` is copied to R2, used here as the `tmp` variable.

`x` 的值被复制到 R2，用作 `tmp` 临时变量。

The value of `y` is loaded to R3 and stored at the address of `x`;

`y` 的值被加载到 R3，然后存储到 `x` 的地址；

And finally the `tmp` value in R3 is stored at the address of `y`.

最后 R3 里的 `tmp` 值被存储到 `y` 的地址。

The end result is that after swap returns the values of `x` and `y` are indeed exchanged, just as you wanted.

最终结果：swap 返回之后，`x` 和 `y` 的值确实互换了，跟你想的一样。

Finally, in the last minute of this lesson I'd like to talk briefly about returning pointers from functions.

最后，趁下课前的这点时间，简单说一下从函数返回指针的问题。

But before I go there, let me finally explain the persistent warning that has been haunting us for a long time. The warning is that the return statement from main is unreachable. This is all fine, because the compiler is smart and sees an endless `while(1)` loop before the return. However, the return type from main must be `int`, because this is required by the C standard. At the same time, the standard also requires that every function with non-void return type always explicitly returns this type. So, it is impossible to satisfy the standard and avoid the IAR warning at the same time. So far, I've opted for standard compliance and portability, because other compilers, such as GNU GCC, for example, will report a warning if the return statement was missing.

不过先说这个之前，让我终于解释一下一直困扰我们好久的那个警告——说 main 里的 return 语句不可达。这其实没问题，因为编译器很聪明，看到 return 前面有个 `while(1)` 死循环。但 main 的返回类型必须是 `int`，这是 C 标准要求的。同时标准还要求每个非 void 返回类型的函数必须显式返回一个值。所以你不可能既满足标准又避免 IAR 的警告。到目前为止我一直选择遵守标准和保证可移植性，因为其他编译器（比如 GNU GCC）在缺少 return 语句时反而会报警告。

But for the sake of finally getting squeaky clean compilations, I will comment out the `return 0` statement in main.

但为了终于获得一个干干净净的编译结果，我还是把 main 里的 `return 0` 注释掉吧。

With this finally out of the way, let's assume that for some reason you want the swap function to remember the (x,y) pair of arguments in the original order and return it as an array. Your first attempt to get this behavior might look as follows:

好了，这个终于解决了。接下来假设你有这样的需求：让 swap 函数记住原始顺序的 (x,y) 参数对，然后作为数组返回。你可能会这么写：

You define a local array `tmp` with the size of two; you fill this array with values of `x` and `y`; you swap `x` and `y` using the array in the reverse order; and finally you return the array; You also modify the return type to match the return statement.

定义一个大小为 2 的局部数组 `tmp`；把 `x` 和 `y` 的值填进去；用数组的逆序来交换 `x` 和 `y`；最后返回这个数组。返回类型也要改成对应的指针类型。

When you compile at this point, the compiler issues a warning, but let's ignore it for now, because you want to see why this is wrong.

编译的时候编译器会报一个警告，但我们先不管它，因为你要亲眼看看为什么这样做是错的。

Instead let's use the new swap function in your code.

我们直接在代码里用这个新的 swap 函数。

The general idea is to keep swapping the delay times for LED on time and off time to make the blinking pattern more interesting.

思路是不断交换 LED 亮和灭的延时时间，让闪烁模式更有趣。

Let's run this code. To better see what happens, you will need to view a little more than the current CSTACK, so setup the raw memory view to show the memory around the stack pointer.

运行代码看看。为了观察得更清楚，你需要看到的范围比当前 CSTACK 视图大一些，所以把原始内存视图设到栈指针附近。

Set the first interesting breakpoint at the return from swap.

在 swap 的返回处设一个有意义的断点。

After you hit this breakpoint, verify that the stack contains the `tmp` array as well as `x` and `y`.

命中断点后，确认栈上确实有 `tmp` 数组以及 `x` 和 `y`。

When you step out of swap, however, the stack contains only `x` and `y`. The `tmp` array is still recognizable in the raw memory view, but now it is above the stack pointer, therefore it is no longer shown in the CSTACK view.

但是当你步出 swap 之后，栈上只剩下 `x` 和 `y`。`tmp` 数组在原始内存视图里还能看到，但它已经在栈指针之上——也就是已经不在栈的有效范围里了，所以 CSTACK 视图不再显示它。

Now, set a breakpoint at the second call to delay and run. When you stop there, notice that the argument `iter` in R0 is zero, instead of expected 500,000. A quick look at the raw memory shows why. In the meantime, the first call to delay used the stack and destroyed the previous value.

好，在第二次调用 delay 的地方设个断点然后运行。停在那儿的时候，注意看 R0 里的参数 `iter`——居然是 0，而不是预期的 500,000。看一眼原始内存就知道原因了：第一次调用 delay 的时候用了栈，把之前的值给覆盖掉了。

So now you see, why returning a pointer to a local variable is always a bad idea, because such pointers will always fall above the stack after the function returns. The more technical term is that all local variables go **out of scope** when the function returns, so they no longer even exist and can't be accessed.

所以你现在明白了——返回指向局部变量的指针永远是个坏主意。因为函数返回后，这些指针指向的地址就在栈指针之上了。更技术性的说法是：函数返回时，所有局部变量都**超出作用域**（out of scope）了，它们不再存在，也不应该被访问。

The remedy for this problem is quite simple, actually. Instead of using local variables on the stack, use local variables that are not on the stack.

解决办法其实很简单：不要用栈上的局部变量，而是用不在栈上的局部变量。

In C the **`static`** keyword used in front of a local variable tells the compiler to allocate the variable outside of the stack, so that it outlives any call to the function and therefore can be accessed even after the function returns.

在 C 语言中，在局部变量前加 **`static` 关键字**，就是告诉编译器把这个变量分配在栈以外的位置，这样它比任何一次函数调用都活得长，函数返回后也依然可以访问。

After this change, the compilation produces no warnings.

改完之后，编译就没有警告了。

When you run this code to the return from swap, you can see that the `tmp` array is no longer on the stack. Instead it is in the regular memory right at the beginning of RAM.

运行代码到 swap 的返回处，你会看到 `tmp` 数组已经不在栈上了——它在 RAM 起始位置的常规内存区域里。

This time around, the second call to delay receives the correct argument of 500,000.

这次，第二次调用 delay 就收到了正确的参数 500,000。

After you remove all the breakpoints and run the program, you can see that the LED blinks as expected.

清掉所有断点让程序自由运行，LED 按预期闪烁。

This concludes this lesson about pitfalls to avoid while working with functions. In the next lesson, you will learn about data structures in C, so that you can start using the Cortex Microcontroller Software Interface Standard (CMSIS) to access the hardware.

关于使用函数时要避开的坑，这节课就讲到这里。下节课你将学习 C 语言中的数据结构，然后就可以开始用 **CMSIS**（Cortex 微控制器软件接口标准）来访问硬件了。

## 术语说明 / Terminology Notes

| 英文术语 | 中文翻译 | 说明 |
|---------|---------|------|
| Stack | 栈 | 后进先出（LIFO）的内存区域，用于存储函数调用信息和局部变量 |

| Stack Frame | 栈帧 | 每次函数调用在栈上分配的空间，包含返回地址、参数和局部变量 |
| Automatic Variable | 自动变量 | 函数内部声明的局部变量，存储在栈上，函数返回后不再有效 |
| Call Stack | 调用栈 | 当前所有嵌套函数调用的栈帧链 |

| Indirection | 间接访问 | 通过指针访问数据的方式，增加一层地址间接性 |

| Startup Code | 启动代码 | 程序运行前由处理器执行的初始化代码，设置栈、堆等 |
| Linker | 链接器 | 将编译后的目标文件合并为最终可执行程序的工具 |
| Heap | 堆 | 用于动态内存分配（`malloc`/`free`）的 RAM 区域 |
| Vector Table | 向量表 | 存放异常和中断处理程序地址的内存区域，位于低地址 |
| Program Counter (PC) | 程序计数器 | CPU 中存储下一条要执行的指令地址的寄存器 |
| LR Register (Link Register) | 链接寄存器 | 存储函数返回地址的寄存器（R14） |
| `volatile` keyword | `volatile` 关键字 | 告诉编译器该变量可能被外部因素改变，不要优化对其的访问 |
| `static` keyword | `static` 关键字 | 用于局部变量时，使其存储在静态内存而非栈上，生命周期贯穿整个程序 |

| Breakpoint | 断点 | 调试时设置在代码中的停止点，程序执行到此处会暂停 |
