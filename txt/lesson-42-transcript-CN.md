The state machine contains six nested states: "s", "s1", and "s11" on the left and "s2", "s21" and "s211" on the right.

这个状态机有六个嵌套状态：左边是 "s"、"s1"、"s11"，右边是 "s2"、"s21"、"s211"。

The various transitions are triggered by events named A, B, C, and so on through I. These events correspond to the ordering of transition types from the simplest to progressively more complex in the state machine algorithm used inside the QP framework.

各种转换由名为 A、B、C 一直到 I 的事件触发。这些事件的顺序恰好对应 QP 框架内部状态机算法中从简单到复杂的转换类型排列。

Also, all transitions as well as states have actions. These actions produce information as to what exactly happened. For instance, entry action to state "s2" produces output "s2-ENTRY", while the exit action produces output "s2-EXIT".

另外，所有转换和状态都带有动作。这些动作会产生输出，告诉你到底发生了什么。比如，状态 "s2" 的**进入动作**（entry action）输出 "s2-ENTRY"，而**退出动作**（exit action）输出 "s2-EXIT"。

Similarly, the action on state transition A in state s1 produces the output "s1-A", while state transition A in s21 produces the output "s21-A".

同理，状态 s1 中转换 A 上的动作输出 "s1-A"，s21 中转换 A 上的动作输出 "s21-A"。

By the way, this kind of output with the information about the code execution is more technically called "software tracing", because the output generated by the instrumentation added to the software allows you to trace the code execution. 顺便说一下，这种包含代码执行信息的输出，技术上更准确的叫法是**软件追踪**（software tracing）——因为通过插桩（instrumentation）代码产生的输出，能让你追踪程序的执行过程。这类信息对于调试、测试和调优代码非常有用。软件追踪是一个很重要的概念，后续课程我会专门讲。

But going back to your state machine, it also demonstrates guard conditions and for that, it has an attribute "foo", which is used inside the guards and also modified in some transitions.

回到这个状态机——它还演示了**守卫条件**（guard condition），为此专门设了一个属性 "foo"，在守卫条件里使用，有些转换中还会修改它的值。

具体来说，状态 "s21" 中的转换 G 一路画到了状态 "s11"，但其实它只需要到 "s1" 这个超级状态就行了。现在 QHsmTst 模型已经修正了。

为此，打开命令提示符，切换到你的 QHsmTst 示例目录。

This directory contains a Makefile, which should work on Windows as well as Linux and MacOS. This Makefile is designed to be easily customizable for your own applications, whereas you typically don't need to change anything beyond that line.

这个目录里有个 Makefile，Windows、Linux、MacOS 都能用。它被设计得很容易定制——一般你只需要改那一行就够了，其他地方不用动。

To execute the Makefile you need the make utility. But, if you've installed QP-bundle, as shown in the last lesson-41, make should be directly available in your path.

执行 Makefile 需要 make 工具。不过如果你已经按第 41 课的说明安装了 QP-bundle，make 应该已经在你的路径里了。

So, now just type "make" to build the code.

好，现在输入 `make` 来构建代码。

This produces the executable in the build directory.

这会在 build 目录下生成可执行文件。

To run this executable from your command-prompt, type build\qhsmtst.

在命令提示符里输入 `build\qhsmtst` 运行它。

This produces some printouts from your software tracing instrumentation inside the state machine actions.

运行后会看到一些打印输出，这些是状态机动作里的软件追踪插桩代码产生的。

By correlating this tracing information to the state diagram, you will be able to see exactly what the state machine is doing and in which order.

把这些追踪信息跟状态图对照着看，你就能清楚地知道状态机在做什么、以什么顺序执行。

Please try to pay attention to the details here, because they are important to learn and understand the semantics of hierarchical state machines.

请注意观察这些细节——它们对理解层次状态机的语义非常关键。

So, starting with the top-most initial transition, the first action "top-INIT" is the one attached to the transition itself. Please note that besides producing the output, the action also initializes the member "foo" to zero. This will be important later for evaluation of guard conditions.

从最顶层的**初始转换**（initial transition）开始看。第一个动作 "top-INIT" 是附加在转换本身上的。注意，除了产生输出，这个动作还把成员 "foo" 初始化为零——后面评估守卫条件时会用到它。

Please also note that an initial transition is allowed to cut through more than one level of state nesting, like here it cuts through state "s" and goes directly to state "s2".

还要注意，初始转换允许穿越多层状态嵌套——比如这里它穿过状态 "s"，直接到达状态 "s2"。

However, every state crossed by a transition (initial or regular) must be still properly entered, and therefore the next action executed is the entry action to state "s", followed by the entry action to state "s2".

但是，转换路径上经过的每个状态（不管是初始转换还是常规转换）都必须被正确进入。所以接下来执行的是状态 "s" 的进入动作，然后是状态 "s2" 的进入动作。

Now, the top-most initial transition ends on state "s2", which is called "the explicit target of the transition", but the trace does not stop there.

最顶层的初始转换结束在状态 "s2"——这叫做"转换的显式目标"——但追踪并没有在这里停下。

This is because the semantics prescribes that any transition, including initial transition, needs to "drill" into the sub-states as long as there are initial transitions nested directly in the target state.

因为语义规定，任何转换（包括初始转换）都需要"钻入"子状态——只要目标状态内部直接嵌套了初始转换。

And indeed, there is an initial transition nested directly in "s2", so it is taken.

确实，"s2" 里直接嵌套了一个初始转换，所以它被执行。

Next, "s21" is entered and "s211" is also entered.

接下来，"s21" 被进入，"s211" 也被进入。

"s211" is called a "leaf state", because it has no further substates or nested initial transitions. Therefore the run-to-completion step completes here and the hierarchical state machine is said to have reached a "stable state configuration".

"s211" 被称为**叶状态**（leaf state），因为它下面没有子状态，也没有嵌套的初始转换。所以**运行到完成步骤**（run-to-completion step）就在这里结束了，状态机此时达到了**稳定状态配置**（stable state configuration）。

The last entered state becomes the current state.

最后进入的那个状态就成为当前状态。

At this point you can start dispatching events to your state machine. You do this by typing on your keyboard. For example, letter G dispatches the corresponding event G to the state machine.

现在你可以开始向状态机**分派**（dispatch）事件了。在键盘上敲字母就行，比如按 G 就把事件 G 分派给状态机。

Per the semantics of hierarchical state machines, the event G is handled in the following way:

根据层次状态机的语义，事件 G 的处理过程是这样的：

First, the current state ("s211") attempts to handle the event. However, state "s211" does not have any transition labeled with G, so the event is passed on to the next higher-level state in the hierarchy, which is state "s21". "s21" has a transition triggered by G, so it executes the action associated with the transition and produces the printout "s21-G;".

首先，当前状态 "s211" 尝试处理这个事件。但 "s211" 上没有任何标记为 G 的转换，于是事件被往上传递到层次结构中的上级状态 "s21"。"s21" 有一个由 G 触发的转换，所以执行关联的动作，打印 "s21-G;"。

Next the state machine executes the transition chain that exits the source state configuration and enters the target state configuration. The transition chain starts with exit actions from all states up the state hierarchy to the so called Least Common Ancestor (LCA), but not exiting the LCA itself.

接下来，状态机执行转换链——退出源状态配置、进入目标状态配置。转换链从退出动作开始：沿着层次结构一路往上退出各个状态，直到所谓的**最近公共祖先**（Least Common Ancestor, LCA），但不退出 LCA 本身。

The LCA of "s21"-"s1" pair of states is their common superstate "s", so all states up to "s", but without "s" itself are exited.

"s21" 和 "s1" 这对状态的 LCA 是它们共同的超级状态 "s"，所以从当前状态一直到 "s" 的所有状态都被退出，但 "s" 本身不退出。

Next the target state configuration is entered in the exact opposite order, that is, starting from highest levels of state hierarchy down to the lowest.

然后目标状态配置以完全相反的顺序被进入——从层次结构的最高层往下，一直到最低层。

The transition G from state "s21" terminates at state "s1". However, "s1" has a nested initial transition, so it is executed and "s11" is entered. This is a leaf state, so the RTC step completes.

从 "s21" 出发的转换 G 终止于状态 "s1"。但 "s1" 内部有个嵌套的初始转换，所以它被执行，"s11" 被进入。这是个叶状态，RTC 步骤就此完成。

Next, let's dispatch event I. Again, the current state "s11" does not have any transitions labeled I, so the event is passed on to the next level of state hierarchy, that is, to state "s1". "s1" has an *internal* transition triggered by I, therefore "s1" handles the event and produces the printout "s1-I;".

接下来分派事件 I。同样，当前状态 "s11" 上没有标记为 I 的转换，事件被传递到上一级状态 "s1"。"s1" 有一个由 I 触发的**内部转换**，所以 "s1" 处理了这个事件，打印 "s1-I;"。

And at this point the processing ends. No change of state ever occurs in the internal transition, even if such transition is inherited from higher levels of state hierarchy. The current state remains the state "s11".

处理到此结束。内部转换永远不会引起状态变更，即使这个转换是从更高层级继承来的。当前状态仍然是 "s11"。

Next, let's dispatch event A. As before, the current state "s11" does not prescribe how to handle A, so the event is passed on to the superstate "s1". "s1" has a *self* transition triggered by A and so it executes actions associated with that transition producing the printout "s1-A;". This time, however, A is a regular transition, which requires exiting the source state configuration and entering the target state configuration.

接下来分派事件 A。跟之前一样，当前状态 "s11" 没有规定如何处理 A，事件被传给超级状态 "s1"。"s1" 有一个由 A 触发的**自转换**（self-transition），执行关联的动作，打印 "s1-A;"。但这次 A 是常规转换，需要退出源状态配置再进入目标状态配置。

The LCA of a state pair "s1" - "s1" is "s", so all states from the current state up to "s", but excluding "s" are exited.

状态对 "s1"-"s1" 的 LCA 是 "s"，所以从当前状态一直到 "s" 的所有状态都被退出，但不包括 "s"。

Next, state "s1" is cleanly re-entered by executing the entry action to "s1", initial transition in "s1", and entering the "s11" leaf state.

然后状态 "s1" 被干净地重新进入：执行 "s1" 的进入动作、"s1" 内部的初始转换，进入叶状态 "s11"。

At this point I'd like to make two observations: The first is that in hierarchical state machines self-transitions, like "s1-A" here, are different from internal transitions, like "s1-I" here.

这里我想指出两点：第一，在层次状态机中，自转换（比如这里的 "s1-A"）跟内部转换（比如 "s1-I"）是不同的。

This is not necessarily the case in the classical, non-hierarchical state machines without entry and exit actions to states, where self-transitions are used exactly to cause a reaction in a given state.

在经典的非层次状态机里就不一样了——那种状态机没有进入和退出动作，自转换就是用来在某个状态里触发一个反应的。

And the second observation is that in hierarchical state machines, a self-transition is an idiom to cleanly *reset* a given state context, by cleanly exiting and re-entering the state again. Such self-transitions can be useful for various "Cancel" operations, like the "Cancel" button in a calculator.

第二点，在层次状态机中，自转换其实是一种干净地**重置**某个状态上下文的惯用模式——通过干净地退出再重新进入。这种自转换对各种"取消"操作很有用，比如计算器上的"取消"按钮。

Now, let's show the current state, which is still "s11" and dispatch event D.

好，看看当前状态——仍然是 "s11"。现在分派事件 D。

"s11" has a transition D, but this transition has a guard [me->foo]. "foo" is an attribute of the state machine, which was initialized to 0 in the top-most initial transition.

"s11" 有一个转换 D，但它带了一个守卫条件 `[me->foo]`。"foo" 是状态机的一个属性，在最顶层的初始转换中被初始化为 0。

Therefore the guard condition [me->foo] evaluates to FALSE. According to the UML semantics, this is treated as though transition D was absent in "s11" and therefore, the event D is passed on to the next higher level, that is, to state "s1".

所以守卫条件 `[me->foo]` 求值为 FALSE。根据 UML 语义，这相当于 "s11" 中不存在转换 D，于是事件 D 被传递到上一级——状态 "s1"。

State "s1" also has transition D, but with the complementary guard [NOT me->foo]. This time, the guard evaluates to TRUE and the transition is taken, producing the "s1-D" trace. Please note that the action on that transition also changes the value of the attribute foo to 1.

"s1" 也有转换 D，但带了一个互补的守卫条件 `[NOT me->foo]`。这次求值为 TRUE，转换被执行，产生 "s1-D" 追踪输出。注意这个转换上的动作还把 foo 的值改成了 1。

After this, all the appropriate exit actions up to the LCA, which is state "s", are taken, followed by entry actions back to "s11". The current state becomes again "s11".

之后，一直到 LCA（也就是状态 "s"）的所有该退出的状态都执行了退出动作，然后一路重新进入回到 "s11"。当前状态又变成了 "s11"。

Now, when you dispatch another event D, the guard [me->foo] in transition s11-D evaluates to TRUE and so this transition is taken. This time the LCA is only "s1", so fewer exit and entry actions are executed.

现在再分派一次事件 D，转换 s11-D 上的守卫条件 `[me->foo]` 求值为 TRUE，转换被执行。这次 LCA 只是 "s1"，所以执行的退出和进入动作更少。

Event C dispatched to the state machine demonstrates again that all exit and entry actions are always executed, regardless of which transitions are in between. For example, the nested initial transition in that explicit target state "s2" goes to substate "s211", cutting through the substate "s21". However, still the entry actions don't skip the entry to "s21".

分派事件 C 再次证明了：所有退出和进入动作都会被执行，不管中间经过了哪些转换。比如，显式目标状态 "s2" 中的嵌套初始转换指向子状态 "s211"，中途穿过 "s21"——但进入动作不会跳过 "s21" 的进入。

This example demonstrates once again the powerful concept of guaranteed cleanup of the source state configuration through the exit actions and guaranteed initialization of the target state configuration through the entry actions, regardless of the complexity of the exit or entry path.

这个例子再次展示了一个强大的概念：不管退出或进入的路径有多复杂，退出动作保证了源状态配置的清理，进入动作保证了目标状态配置的初始化。

Interestingly, in hierarchical state machines, the exact same transition can cause different sequences of exit actions, depending on which state inherits the transition.

有意思的是，在层次状态机中，完全相同的转换可能产生不同的退出动作序列——取决于继承这个转换的是哪个状态。

For example, let's now dispatch event E twice in a row.

比如，现在连续分派两次事件 E。

Each time, the event triggers the same transition "s-E", but the actions executed are different, because transition E fires from different state configurations: once when the current state is "s211", and next when the current state is "s11".

每次触发的是同一个转换 "s-E"，但执行的动作不一样，因为转换 E 是从不同的状态配置中触发的：一次是当前状态为 "s211"，另一次是 "s11"。

Finally, guard conditions can also be used on internal transitions.

最后，守卫条件也可以用在内部转换上。

For example, let's now dispatch event G to change the current state to "s211".

比如，先分派事件 G 把当前状态切换到 "s211"。

And after this, two events I in a row.

然后连续两个事件 I。

The first I triggers transition "s2-I", because the guard [NOT me->foo] is TRUE. Please note that the action on this transition also sets foo to 1.

第一个 I 触发了转换 "s2-I"，因为守卫条件 `[NOT me->foo]` 为 TRUE。注意这个转换上的动作还把 foo 设为 1。

The next event I does not trigger "s2-I", because this time the guard [NOT me->foo] evaluates to FALSE, and so the event is passed up to the superstate "s".

下一个 I 就不触发 "s2-I" 了，因为这次守卫条件 `[NOT me->foo]` 求值为 FALSE，事件被往上传递到超级状态 "s"。

The internal transition "s-I" has a complementary guard, which is TRUE, so the transition "s-I" is taken.

内部转换 "s-I" 有一个互补的守卫条件，值为 TRUE，所以 "s-I" 被执行。

Of course, in case of internal transitions there is no change of state, so no exit or entry actions are ever executed.

当然，内部转换不会发生状态变更，所以退出和进入动作都不会执行。

现在按 Escape 键终止 QHsmTst 程序。不过你完全可以自己跑这个示例、分派各种事件、研究它产生的追踪输出，这样能学到更多。

But perhaps a better idea is to make a local copy of the example and make any changes there.

但更好的做法是把示例复制一份出来，在副本上改。

So, let's just do that as a coding exercise for today.

好，我们就把这件事当作今天的编码练习。

| transition | 转换 | 状态之间由事件触发的迁移 |
| entry action | 进入动作 | 进入状态时自动执行的动作 |

| superstate | 超级状态 | 包含其他子状态的父状态 |
| propagate | 传播 | 事件从子状态向更高级别状态传递的过程 |
