## Embedded Assertions

## 嵌入式断言

So, let's see how to implement assertions in an embedded-systems-friendly way. Here, I will quickly review the implementation consisting of a single header file, "qassert.h," located in the qpc framework. This is a self-contained file and you can use it outside the QPC framework in your own projects. Actually, you've been already using these assertions on multiple occasions, for example, in the lessons about the RTOS.

好，来看看怎么用对嵌入式系统友好的方式来实现断言。我这里快速过一遍 QPC 框架里的实现——其实就一个头文件 `qassert.h`。它是自包含的，你完全可以在 QPC 框架之外的项目中使用。实际上，你之前已经用过这些断言了，比如 RTOS 相关的课程里就用到了。

Usually, I would review the raw file, but today I'd like to show you a review of the documentation generated by doxygen because it's often an easier way to explore the code.

通常我会直接看源码文件，但今天我想给你看看 Doxygen 生成的文档——这往往是浏览代码更方便的方式。

The documentation is located in the QP online manual that can be found on the state-machine.com website through the Products/QPC-Manual menu. To find quickly what you need, type "qassert" into the search box.

文档在 QP 在线手册里，通过 state-machine.com 网站的 Products/QPC-Manual 菜单就能找到。要快速定位你想要的内容，在搜索框里输入 "qassert" 就行。

The first documented macro is Q_ASSERT_ID(), which is a general-purpose assertion used later for all other assertion variants. The macro takes two parameters: the ID number, which should be unique within a given module, and the Boolean expression to check.

文档里第一个宏是 `Q_ASSERT_ID()`，这是一个通用断言宏，后面所有其他断言变体都基于它来实现。它接受两个参数：ID 编号——在同一个模块内应该唯一——以及要检查的布尔表达式。

The macro itself is defined by means of the ternary operator, which is standard practice. For example, here is the standard <assert.h> header file from the ARM-KEIL compiler-6 that you've been using through uVision IDE. The ternary operator is used to define all versions of the assert() macro in that file.

这个宏本身是通过**三元运算符**（ternary operator）来定义的，这是标准做法。举个例子，你在 uVision IDE 中一直用的 ARM-KEIL 编译器-6 的标准 `<assert.h>` 头文件就是这样的——里面所有版本的 `assert()` 宏都用三元运算符来定义。

A significant advantage of defining assert as an expression as opposed to a statement, is that it can be safely used inside if-else control-flow. If you defined assert() as an if-statement, you could run into the dangling-else problems. The else branch from your code could be misunderstood as else from the assertion if-statement.

把 assert 定义成表达式而不是语句，有一个很大的好处：它可以安全地用在 if-else 控制流里。如果你把 `assert()` 定义成 if 语句，就可能碰到**悬空 else 问题**（dangling-else problem）——你代码里的 else 分支会被误认为是断言那个 if 语句的 else。

But going back to the Q_ASSERT_ID() definition, the boolean expression "expr_" is evaluated, and if it's true, the ternary operator returns zero cast on void, just like the standard assert. Otherwise, the ternary operator calls the Q_onAssert() function, which, as you can expect, will be your custom error handler.

回到 `Q_ASSERT_ID()` 的定义。布尔表达式 `expr_` 被求值，如果为真，三元运算符返回一个转换为 void 类型的零——跟标准 assert 一样。如果为假，三元运算符就调用 `Q_onAssert()` 函数。你大概猜到了，这就是你自己定义的错误处理函数。

To uniquely identify the specific assertion, the Q_onAssert() callback function takes the ID parameter and the `Q_this_module_` string. This is a departure from the standard practice of identifying assertions with the __LINE__ number and the __FILE__ string.

为了唯一标识到底是哪个断言触发了，`Q_onAssert()` 回调函数接收 ID 参数和 `Q_this_module_` 字符串。这跟用 `__LINE__` 行号和 `__FILE__` 文件名来标识断言的标准做法不太一样。

Why depart from the beaten path? Well, __LINE__ is quite an unstable ID for an assertion because adding or removing lines changes all the following line numbers. As I will discuss in a minute, testing assertions requires a *stable* way of identifying them.

为什么要偏离惯例呢？因为 `__LINE__` 作为断言 ID 实在太不稳定了——你加一行或删一行，后面所有的行号全变了。我稍后会讨论到，测试断言需要一种**稳定的**标识方式。

Similarly, the string generated by __FILE__ often depends on how the file is specified to the compiler. If the file is specified with the path name, __FILE__ expands accordingly. Also, if you use multiple assertions in a given file, some embedded compilers might generate multiple copies of the file string, which is wasteful.

类似地，`__FILE__` 生成的字符串也取决于文件是怎么传给编译器的——如果带路径，`__FILE__` 就会展开成带路径的形式。而且，如果一个文件里用了多个断言，有些嵌入式编译器会生成文件字符串的多个副本，纯属浪费。

To avoid all such problems, the qassert header file provides a macro Q_DEFINE_THIS_MODULE(), where you can define your own module name string, typically at the top of each module. That static and const pointer will be subsequently used in all assertions in a given file.

为了避免这些问题，qassert 头文件提供了一个宏 `Q_DEFINE_THIS_MODULE()`，让你定义自己的模块名称字符串——通常放在每个源文件的开头。这个静态的 const 指针随后会被该文件中所有断言共用。

Going back to the Q_onAssert() function, it is defined as never returning with the Q_NORETURN macro. If that macro is not defined elsewhere, the default definition uses the C99 _Noreturn specifier. This can help the compiler to perform optimizations as execution paths that violate asserted conditions are unreachable.

回到 `Q_onAssert()` 函数。它通过 `Q_NORETURN` 宏标记为永不返回。如果这个宏没有在其他地方定义，默认会用 C99 的 `_Noreturn` 说明符。这能帮助编译器做优化——因为违反断言条件的那些执行路径本来就是不可达的。

Additionally, if you use static analysis tools, the Q_onAssert() function should be given the "no return" semantics, like it is done in the QPC framework for the PC-Lint-Plus static analysis tool. This helps the tool to better understand your code and avoid diagnostics for asserted conditions.

另外，如果你用**静态分析工具**（static analysis tools），应该给 `Q_onAssert()` 函数标注"不返回"的语义——QPC 框架里对 PC-Lint-Plus 就是这样做的。这样工具就能更好地理解你的代码，避免对已断言的条件产生误报。

Now, qassert.h provides many other assertion variants, such as Q_REQUIRE(), Q_ENSURE(), and Q_INVARIANT(). These correspond to preconditions, postconditions, and invariants, respectively. The names of the macros are direct loans from the Eiffel programming language that natively supports Design by Contract.

qassert.h 还提供了很多其他断言变体，比如 `Q_REQUIRE()`、`Q_ENSURE()` 和 `Q_INVARIANT()`。它们分别对应**前置条件**（preconditions）、**后置条件**（postconditions）和**不变量**（invariants）。这些宏的名字直接借用了 Eiffel 语言的命名——Eiffel 是原生支持按契约设计的编程语言。

The most useful and most frequently used are preconditions, which you designate with the macro Q_REQUIRE_ID(), or Q_REQUIRE(). Preconditions are specified inside the functions, but they spell out contractual obligations for the callers of these functions. So, when a precondition assertion fails, you know the problem is not with the function but rather an incorrect call to that function.

最实用、也最常用的是前置条件，用 `Q_REQUIRE_ID()` 或 `Q_REQUIRE()` 宏来标记。前置条件写在函数内部，但它声明的是调用者必须遵守的契约义务。所以，当前置条件断言失败时，你知道问题不在函数本身——而是调用这个函数的方式不对。

Using a precondition assertion, as opposed to just a generic assertion, is an excellent way of documenting a function and providing a hint as to where the problem might be. In that way, preconditions should be an integral part of the function's documentation, just like the list of parameters, because the callers of the function should know and satisfy the preconditions.

用前置条件断言而不是普通通用断言，是给函数写文档、提供排错线索的好办法。前置条件应该成为函数文档不可分割的一部分——就像参数列表一样，因为调用者需要了解并满足这些前置条件。

The other variants of assertions, like postconditions and invariants, are less frequently used but also provide valuable documentation as to the purpose of these assertions.

其他断言变体——比如后置条件和不变量——用得少一些，但同样能提供有价值的文档信息，告诉你这些断言的用途是什么。

Another frequently used assertion variant is Q_ERROR(), which simply calls Q_onAssert(). This one is useful for incorrect paths through the code, such as unwanted events in a state machine.

还有一个常用的断言变体是 `Q_ERROR()`，它直接调用 `Q_onAssert()`。这个宏专门用来标记代码中的错误路径，比如状态机中收到了不该出现的事件。

## The Assertion Handler

## 断言处理函数

Regarding the Q_onAssert() handler, in the traditional use of assertions only during debugging, you might get away with a simplistic implementation, such as an endless loop. That way, when an assertion happens, you can break into the program with a debugger and find it conveniently spinning inside Q_onAssert(). You can then inspect the call stack to see where the assertion fired.

说到 `Q_onAssert()` 处理函数——如果你只在调试阶段用断言，那简单写个死循环也能凑合。断言触发时，你用调试器暂停程序，就会看到它在 `Q_onAssert()` 里转圈。然后查看调用栈，就能知道是哪里触发了断言。

But you can also leave assertions enabled in the final product, which I will strongly advocate in a minute. In that case, the assertion handler becomes critically important as your last line of defense after detecting an error.

但你也可以在最终产品里保留断言——我稍后会强烈推荐这种做法。到那时，断言处理函数就变得至关重要了，它是检测到错误后的**最后一道防线**。

To provide real protection, however, the assertion handler must be carefully designed to perform damage control and corrective actions for your specific system. Please remember that the assertion handler should not return, so most of the time, it should end with resetting the system. For that, the CMSIS provides the function NVIC_SystemReset().

不过，要真正起到保护作用，断言处理函数必须经过精心设计，针对你的具体系统做损害控制和纠正操作。记住，断言处理函数不应该返回——大多数情况下，它应该以系统复位作为结束。为此，CMSIS 提供了 `NVIC_SystemReset()` 函数。

Also, please remember that the assertion handler runs after your system has already been compromised. For that reason, the assertion handler is NOT your "usual code" and must be carefully tested under various fault conditions, such as stack overflow, interrupt preemption, etc.

还有一点要记住：断言处理函数运行时，系统已经被破坏了。正因如此，断言处理函数**不是**你的"常规代码"——必须在各种故障条件下仔细测试，比如**栈溢出**（stack overflow）、中断抢占等等。

For such testing, I highly recommend the fault-injection technique you saw in several lessons of this video course. For example, you can intentionally change the stack pointer (SP) register to simulate stack overflow and then cause an assertion failure.

做这类测试，我强烈推荐**故障注入**（fault injection）技术——你在这门课的前面几节课中已经见过了。比如，你可以故意修改栈指针（SP）寄存器来模拟栈溢出，然后触发一个断言失败。

## Assert Handler and Exceptions

## 断言处理函数与异常

In programming languages that support throwing and catching exceptions, such as C++, assertion handlers often throw exceptions. In my opinion, this is a mistake for a couple of reasons.

在支持异常抛出和捕获的语言中（比如 C++），断言处理函数经常会抛出异常。但在我看来，这是不对的，原因有两个。

First, throwing an exception makes sense only if that exception can be caught and reasonably handled with the intent to continue program execution. None of this applies if assertions are used correctly.

第一，抛出异常只有在这个异常能被捕获、能被合理处理、并且程序打算继续运行时才有意义。但如果断言用得正确，这些前提全都不成立。

And second, throwing an exception involves unwinding the stack, which implicitly assumes that the stack hasn't been compromised.

第二，抛出异常涉及**栈展开**（stack unwinding），这隐含地假设栈还是完好的。

The main purpose of the fuse analogy was to recognize that the power of assertions derives from their simplicity. You should keep the assertion handler as simple as possible because any complications, such as throwing exceptions, only increase the chance of failures while already in a compromised situation, thus defeating the purpose of effective damage control.

前面用保险丝来打比方，核心想说的就是：断言的力量恰恰来自它的简单。你应该让断言处理函数尽可能简单——任何复杂操作（比如抛出异常）只会增加在已经出问题的情况下再次失败的概率，反而违背了有效损害控制的初衷。

## Hardware Assertions

## 硬件断言

So far, this lesson was only about software assertions placed explicitly in the source code. But there are also several failure conditions detected in hardware. For example, in the lessons about the startup code, you've seen so-called fault exceptions, such as HardFault, MemManage, BusFault, and UsageFault.

到目前为止，我们只讨论了源代码中手动添加的软件断言。但硬件也会检测到一些故障。比如，在讲启动代码的课程中，你见过所谓的**故障异常**（fault exceptions）——HardFault、MemManage、BusFault 和 UsageFault。

Traditionally, these conditions haven't been seen as related to assertions, but for all intents and purposes, the hardware fault handlers and the assertion handler have the same function.

传统上，这些硬件故障不被人跟断言联系在一起。但实际上，硬件故障处理函数和断言处理函数干的是同一件事。

Unlike software assertions, you cannot disable hardware faults in the final product, so you cannot get away with fault handlers coded as endless loops (unless, that is, the users of your device can tolerate permanent "denial of service").

跟软件断言不同，硬件故障在最终产品里是没法禁用的，所以你不能把故障处理函数写成死循环就完事——除非你的设备用户能容忍永久的"拒绝服务"。

Therefore, since you must implement a robust fault handler anyway, you might as well develop just one common handler for both hardware and software assertions.

所以，既然你无论如何都得实现一个健壮的故障处理函数，不如干脆为硬件断言和软件断言开发一个统一的处理函数。

This is precisely how the startup code that you've been using in most of the lessons in this course is structured. As you can see, the fault handlers branch to assert_fail(), which carefully resets the stack pointer, in case of stack overflow, and then it calls the familiar Q_onAssert() handler.

你在本课程大部分课中用的启动代码，正是这样组织的。可以看到，故障处理函数会跳转到 `assert_fail()`，它会小心翼翼地重置栈指针——防止栈溢出的情况——然后调用你熟悉的 `Q_onAssert()` 处理函数。

## Impacts of Assertions

## 断言的影响

As I confessed in the introduction, assertions helped me more than any other programming technique. For example, if you search the Quantum Leaps Free Support Forum for "assert," you will find 23 pages of posts. Many start with an assertion failure report and end with an observation of how difficult the bug would be to find and fix without the particular assertion.

正如我在开头所说，断言对我的帮助比任何其他编程技术都大。举个例子，你在 Quantum Leaps 免费支持论坛搜索 "assert"，能翻到 23 页的帖子。很多帖子都是以断言失败报告开头的，最后都会感叹：如果没有那条断言，这个 bug 得多难发现和修复啊。

But you don't need to take only my word for it. One of the rules for developing safety-critical code by NASA JPL Laboratory for Reliable Software is not only to use assertions but to achieve a sufficient density of about two assertions per function.

你也不用光听我一个人的。NASA JPL 可靠软件实验室制定的安全关键代码开发规则中，不仅要求使用断言，还要求达到足够的密度——大约每个函数两个断言。

Also, Microsoft Research published a paper showing studies of commercial software projects where modules with a low density of assertions had much higher post-release bug rates than those seeded with many assertions.

微软研究院也发表过一篇论文，他们对商业软件项目做了研究，发现断言密度低的模块，发布后的缺陷率远高于大量使用断言的模块。

By the way, links to all papers and resources that I mention will be provided in the video description.

顺便说一下，我提到的所有论文和资源的链接都会放在视频描述里。

As Bertrand Meyer remarked: "The use of assertions will completely change your approach to software construction and in particular your view of errors."

正如 Bertrand Meyer 所说："使用断言将彻底改变你构建软件的方式，尤其是你对错误的看法。"

Working with software programmed "offensively" with assertions feels completely different than with software programmed "defensively."

写"**进攻式**"（offensive）编程的代码——也就是到处加断言——跟写"**防御式**"（defensive）编程的代码，体验完全不一样。

With the recommended density of assertions, the software stops producing undesired behavior, denial of service, or crashes. All bugs manifest themselves as assertion failures. This effect is truly amazing.

当断言密度达到推荐水平后，软件不再出现莫名其妙的行为、拒绝服务或者崩溃。所有的 bug 都会表现为断言失败。这种效果真的很惊艳。

The integrity checks embodied in assertions prevent the code from "wandering around." Even hardware failures and broken builds don't crash and burn, but end up in the assertion handler.

断言中的完整性检查能防止代码"漫无目的地乱跑"。即使是硬件故障或者错误的构建，也不会导致崩溃——而是最终进入断言处理函数。

Once an assertion fires, dismissing the problem as an intermittent "glitch" is much harder, so all errors require attention. You also have a record in the form of the unique assertion-id to start your investigations. This makes most bugs more transparent.

断言一旦触发，你就很难再把问题当作偶发的"毛刺"搪塞过去了——所有错误都必须认真对待。而且你手上还有唯一的断言 ID 作为记录，可以直接从这里开始排查。这让大多数 bug 变得透明多了。

In contrast, testing defensively programmed code is inconclusive. You might be running tests for days and nights, but you can never be sure if the runs were truly successful or perhaps the program silently produced garbage all night long.

相比之下，测试防御式编程的代码是得不出明确结论的。你可能没日没夜地跑了好多测试，但你永远没法确定这些运行是否真的成功了——也许程序整晚都在悄无声息地产生垃圾数据。

## Disabling Assertions

## 禁用断言

As I already mentioned, software assertions can be disabled, and the standard practice is to use them only during debugging but disable them entirely in the final product.

前面已经说了，软件断言可以禁用。标准做法是只在调试期间开启，最终产品里完全关掉。

For example, here is what I heard just yesterday from one engineer working on a medical device: "We don't have assertions enabled for the released version of our codebase. The goal is to detect and fix assert failures during development."

举个例子，就在昨天我听到一位做医疗设备的工程师说："我们发布版本的代码库里没有启用断言。目标是在开发阶段就把所有断言失败检测出来并修复。"

I absolutely agree with the second sentence: to do everything in our power to fix all bugs during development and never fail assertions in the final product.

后半句我完全同意——确实应该在开发阶段尽一切努力把 bug 修掉，确保最终产品里断言永远不会触发。

But once assertions have been used and tested, I don't really understand the logic behind disabling assertions. All the analogies for forming the proper mental model of assertions also show that disabling assertions is, frankly, ridiculous.

但断言既然用了、也测过了，我真的不理解为什么还要禁用它。所有帮助我们正确理解断言的类比都说明，禁用断言——坦率地讲——是很荒谬的。

If you think of assertions as fuses, would you replace all the fuses with nails, coins, and paper clips for real use? How would you feel if you discovered a fuse box "fixed" like that in a car you are about to drive or an airplane you are about to fly? It wouldn't inspire much confidence in your safety. Would it? Yet, this is precisely what disabling assertions does to the code.

如果把断言比作保险丝，你会不会在正式使用时把保险丝全换成钉子、硬币和回形针？如果你发现自己要开的车、或者要坐的飞机里保险丝盒被这么"修"过，你心里什么感觉？安全感肯定大打折扣，对吧？然而，禁用断言对代码做的，跟这完全是一回事。

If you think of assertions as guardrails, would you prefer to drive on a mountain road with or without them? I mean, you never intend to hit a guardrail anyway, so you don't need it, right?

如果把断言比作公路护栏，在有护栏和没护栏的山路上开车，你选哪个？反正你也不打算撞护栏，所以不需要它，对吧？

Finally, if you view assertions as an insurance policy, would you cancel it right before a fire season? I mean, you don't really want to cash such a policy, do you? But if your house burns down anyway, it sure helps to have a damage control mechanism in place.

最后，如果把断言比作保险，你会在火灾季来临之前退保吗？你并不真的想拿到那笔理赔，对吧？但如果房子真的着了，有个损害控制机制在总是好的。

I hope you get the picture...

希望你明白我的意思了……

## 术语说明 / Terminology Notes

| 英文术语 | 中文翻译 | 说明 |
|---------|---------|------|
| Assertion | 断言 | 在代码中检查特定条件是否为真的机制，失败时触发错误处理 |
| Design by Contract (DBC) | 按契约设计 | 一种软件设计方法，通过前置条件、后置条件和不变量定义软件组件间的契约 |
| Precondition | 前置条件 | 函数执行前调用者必须满足的条件 |
| Postcondition | 后置条件 | 函数执行完毕后必须保证的结果条件 |
| Invariant | 不变量 | 在对象生命周期中始终保持为真的条件 |
| Ternary operator | 三元运算符 | C 语言中的 `?:` 运算符，根据条件选择两个值之一 |
| Dangling-else problem | 悬空 else 问题 | if-else 嵌套时 else 分支归属产生歧义的问题 |
| `_Noreturn` specifier | `_Noreturn` 说明符 | C99 标准中的函数说明符，表示函数不会返回调用者 |
| Static analysis tool | 静态分析工具 | 不运行代码的情况下分析代码以发现潜在问题的工具 |
| Fault injection | 故障注入 | 通过故意引入故障来验证系统容错能力的测试技术 |
| Stack overflow | 栈溢出 | 栈空间被耗尽，导致内存越界和不可预测行为 |
| Stack unwinding | 栈展开 | 异常抛出时逐层销毁栈帧的过程，C++ 异常处理的核心机制 |
| Fault exception | 故障异常 | ARM Cortex-M 中的硬件异常类型，如 HardFault、BusFault 等 |
| NVIC_SystemReset() | NVIC 系统复位 | CMSIS 提供的函数，用于执行微控制器系统级复位 |
| Doxygen | Doxygen | 从源代码生成文档的工具，广泛用于 C/C++ 项目 |
| Offensive programming | 进攻式编程 | 使用断言主动检测错误的编程风格，与防御式编程相对 |
| Defensive programming | 防御式编程 | 编写能容忍错误输入和异常情况的代码的风格 |
| `Q_DEFINE_THIS_MODULE()` | `Q_DEFINE_THIS_MODULE()` 宏 | qassert.h 中用于定义当前模块名称字符串的宏 |
| `Q_onAssert()` | `Q_onAssert()` 处理函数 | 断言失败时调用的回调函数，由用户自定义实现 |
| `NVIC` | 嵌套向量中断控制器 | ARM Cortex-M 中的中断控制器，也提供系统复位功能 |
| CMSIS | Cortex 微控制器软件接口标准 | ARM 提供的标准化软件接口，简化 Cortex-M 微控制器编程 |
| `HardFault` | 硬件故障 | ARM Cortex-M 中最高优先级的故障异常，通常表示严重错误 |
| Eiffel | Eiffel 语言 | 原生支持按契约设计的面向对象编程语言 |
| Bertrand Meyer | Bertrand Meyer | 按契约设计方法的发明者，Eiffel 语言的设计者 |
| `Q_ASSERT_ID()` | `Q_ASSERT_ID()` 宏 | QPC 框架中的通用断言宏，接受唯一 ID 和布尔表达式 |
| `Q_REQUIRE_ID()` | `Q_REQUIRE_ID()` 宏 | QPC 框架中的前置条件断言宏 |
| `Q_ENSURE()` | `Q_ENSURE()` 宏 | QPC 框架中的后置条件断言宏 |
| `Q_INVARIANT()` | `Q_INVARIANT()` 宏 | QPC 框架中的不变量断言宏 |
| `Q_ERROR()` | `Q_ERROR()` 宏 | QPC 框架中用于标记不可达或错误代码路径的断言宏 |
